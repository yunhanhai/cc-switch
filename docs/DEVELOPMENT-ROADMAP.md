# YunSwitch 后续开发路线

2026-11-14，基于当前 `.7` 已公开能力及本轮源码复查制定。YunSwitch 已具备独立产品、数据目录、安装身份和发布入口，继续在 CC Switch 基础上维护并保留来源。下一阶段优先提高长时间使用的可靠性和可诊断性，按有证据的场景扩展能力。

## 当前判断

已公开 Windows x64 版本验证了安装、相邻版本升级、合成迁移、设置保留、代理重启、原生 Codex 历史兼容、输出前错误恢复、压缩流及状态请求重发保护。每版记录见[发布准备](RELEASE-READINESS.md)。这些证据来自源码测试及合成上游，真实供应商、套餐、模型和长会话没有全量验证。

复查发现 `.7` 的共享冷却仅调整候选优先级：已经遇到 429 的并发请求仍各自醒来重试，后来延长的冷却也不会改变原有 sleep。这是本轮先处理的缺口。`.8` 准备源码增加每供应商恢复许可，并动态检查共享期限；普通首次请求和已开始的输出仍按现有路径处理。

## 推进顺序

| 顺序 | 工作                   | 用户收益                                                     | 完成证据                                                                                                  |
| ---- | ---------------------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------- |
| 1    | 限流恢复协调与预算     | 减少同一供应商的并发恢复冲击，避免忽略后来延长的 Retry-After | 并发回环、冷却延长、取消/超时、输出后释放，以及便携和升级后程序验收                                       |
| 2    | 请求诊断与可解释状态   | 能分清是在等限流、排队、尝试备用，还是已经返回错误           | 按应用与请求聚合的脱敏状态；不保存密钥、私人正文或工具参数；可定位一次失败链                              |
| 3    | 接入与长会话验证矩阵   | 知道哪些客户端、协议、模型与套餐确实可用                     | 依照[供应商目录](PROVIDER-CATALOG.md)记录版本、环境、协议、生成/流式/工具/长上下文结果，未知保持未知      |
| 4    | 协议转换的独立场景完善 | 多种模型和供应商能可靠承接客户端请求                         | 分别覆盖 Responses、Chat、Messages 转换中的工具调用、推理、token 统计和终态；状态不可重建时返回可操作指引 |
| 5    | 跨平台安装、签名与更新 | 可安装、可升级，且能确认发布者和产物来源                     | 对各平台分别做实际安装和升级验收；具备 YunSwitch 自有签名和更新链后再启用更新                             |
| 6    | 其他开源能力接入       | 扩展功能同时保持单人可维护                                   | 每项引入记录固定来源与许可、用途、协议边界和回归；一次只完成一个可审阅能力                                |

第二项建议复用现有错误分类、请求状态与日志，先提供脱敏摘要，不依靠保存完整请求体排查。界面等待反馈应区分计划等待时长与实际耗时，并能显示每个应用的多个活跃等待；这部分需要独立实现和验证，不作为本轮已完成能力。

第三项先构建统一验证格式和模拟场景，再由使用者按自己的授权配置测试实际供应商。真实请求可能消耗费用，不自动读取本机其他客户端的密钥、会话或配置来做验证。对官方账号、第三方 API 和跨协议转换分别记录结果，不以某一条路径成功推断全部兼容。

## 每一阶段的实施方式

1. 用明确场景说明缺口，先复现当前行为和应有结果。
2. 保持已有设置与数据兼容，确认新行为的适用范围、等待预算和取消路径。
3. 完成有意义的回归和源码检查；涉及程序运行时行为时，验证真实打包程序。
4. 两端 PR、主分支、标签和附件保持同批来源，发布文档只写实际执行过的结果。
5. 一阶段完成后再选择下一项，避免把代码整理、依赖批量升级和新能力混在同一改动里。

## 产品与兼容边界

继续使用 YunSwitch 名称和现有独立安装/数据身份。内部旧可执行文件、数据库名和协议兼容字段按迁移收益逐项评估，改名不能提高请求可靠性，且可能破坏旧配置和升级。

原生 Codex 的加密历史兼容属于可选且可能改变上下文的修复，默认继续关闭。自动重试保持有限预算；已有文本、推理或工具活动后不自动重放。状态型任务和服务器执行工具不能因尚未看到字节就被认定可重复执行。范围见[恢复说明](CODEX-STREAM-RECOVERY.md)。

图标来源整理与依赖更新继续通过各自 PR 审阅，保留第三方许可和现有工作记录。采用其他开源项目时更新[来源台账](PROVENANCE.md)，不删除历史或把继承代码声明为全部原创。

## 本轮范围

`.8` 先完成第一项：已限流请求的恢复协调、共享截止时间、等待预算和取消回收。新机制限制同一应用、同一供应商的输出前恢复尝试，不是对所有 API 流量设置总并发上限，也不保证供应商不会继续返回 429。发布与实际验证状态见[`.8` 记录](releases/3.20.1-yunswitch.8.md)。

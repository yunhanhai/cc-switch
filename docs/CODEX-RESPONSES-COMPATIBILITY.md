# Codex Responses 兼容与自动重试

`3.20.1-yunswitch.4` 源码增加“Codex 加密历史兼容”开关，并修复最终 429 在 Codex 错误响应路径的状态映射与 `Retry-After` 传递。`3.20.1-yunswitch.4` Windows 包已公开；旧 `.3` 包不包含这些改动。构建、安装与升级记录见[`.4` 发布记录](releases/3.20.1-yunswitch.4.md)。

## 当前独立维护与功能状态

YunSwitch 已拥有独立仓库、名称、应用 ID、配置目录、深链和发布渠道，开发版与正式版目录隔离。它仍是基于 CC Switch v3.20.1 的持续二次开发，保留 MIT 来源、协议转换实现和部分内部兼容名称；“独立维护”不等于所有代码重新编写，也不等于所有 API 网站都已验证。

此前发布完成了 Windows 安装与升级、模拟代理、合成数据迁移等验收。付费供应商连通性、所有模型和长会话仍需按实际组合验证，不能把 CI 通过写成“全部功能问题已解决”。

## 使用兼容开关

在**设置 → 路由 → 整流器 → Codex 加密历史兼容**开启；同时开启整流器总开关，启动本地代理并让 Codex 请求经过 YunSwitch。设置保存后对新请求生效，无需额外启动 Node shim。默认关闭，旧配置没有该字段时继续关闭。

适用范围为 Codex 使用 API Key 的**原生 Responses**请求，包括 `/responses`、`/v1/responses` 对应的本地入口，不按供应商网站域名限制。全 URL 类型上游同样按 Codex 请求入口处理。官方账号/OAuth、转换到 Chat Completions 或 Anthropic 的路径沿用各自历史处理，`/responses/compact`、模型列表、其他客户端和直接绕过本地代理的请求不执行此修复。

开启后，对出站请求的协议历史处理：

- 去除回放的 `reasoning` 条目，以及 `content` / `output` 协议数组中的嵌套 `encrypted_content` 块。
- 对包含完整显式内容的消息、函数调用和工具结果去除资源绑定的条目 `id`，保留 `call_id`、调用配对、`phase`、明文内容、模型和缓存设置。
- 仅沿明确协议容器处理；不遍历工具参数 JSON 字符串、任意工具结果对象、元数据、工具定义或用户文本中的同名字段。
- 只改本次发往上游的请求副本；不写回用户历史。错误日志只包含修复计数与供应商 ID，不记录密文和请求内容。

此兼容方式适用于池化网关无法解密其他资源生成的历史状态。删除加密推理会减少可回放上下文，不能用于恢复原本只存在于密文里的信息。因此遇到 `previous_response_id`、`conversation`、压缩历史、仅有 ID 的引用、不完整条目或清理后只剩空内容时，会返回明确的 400 指引；应改用完整显式历史/明文摘要，或关闭此开关并保持原资源会话。不会将这些状态静默删除后伪装为成功。

## 限流、重试与“自动继续”的边界

`.5` 已进一步识别原生 Responses 输出前的 HTTP 200 流内错误，见[恢复说明](CODEX-STREAM-RECOVERY.md)。以下表格保留 `.4` 的历史边界；`.5` 的实际验证与恢复范围见[发布记录](releases/3.20.1-yunswitch.5.md)。

以下均要求请求经过本地代理。设置位于**设置 → 路由 → 故障转移 → Codex**，Codex 接管启用后可配置。

| 情形                            | 实际处理                                                                                                            | 默认与限制                                                                                                         |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| HTTP 429                        | 开启“429 限流等待重试”后优先遵守 `Retry-After` 秒数/日期；缺失或为 0 时按 1、2、4、8、16、30 秒退避，后续封顶 30 秒 | 默认关闭；每家最多 10 次等待重试。默认单次等待上限 120 秒，可设 5–600 秒；上游要求超过上限时转入故障转移或返回错误 |
| 连接失败、408/409/425、5xx      | 按“同一供应商重试”次数和退避设置重发，再考虑备用供应商                                                              | 默认 0 次；最多 10 次，默认 1000ms 初始/8000ms 单次上限。对同一家不重试鉴权、余额不足、参数错误或已等待超时的请求  |
| 切换备用供应商                  | 开启故障转移且已有可用候选路由时，按策略尝试后续供应商                                                              | `maxRetries` 表示额外尝试的供应商数量，默认 3，即最多 4 家；不保证它们拥有相同模型、上下文或配额                   |
| 余额耗尽、401/403               | 同一家盲目重试通常无效；有合适备用渠道时按既有规则转移                                                              | 不会刷新余额、绕过限流或替用户重新登录；官方账号流程有独立限制                                                     |
| HTTP 200 内的 `response.failed` | 新增请求清理可预防由不兼容密文造成的一类失败；其它语义错误仍由响应处理和客户端处理                                  | 当前原生 Codex Responses 透传不能保证所有 SSE 错误都在输出前识别；不把任意流内错误统一算作 HTTP 429                |
| 已经输出的流中断                | 向客户端返回实际错误                                                                                                | 不重放、不拼接半段文本，不自动让编程代理“继续任务”；这样做会重复文本、工具调用或计费                               |

客户端也可能有独立的等待和重试上限，多个配置不能理解成“无限等待直到成功”。可从 429 单次上限 120 秒、同一家重试 2 次/1000ms→8000ms 开始评估，再依据供应商约定与客户端超时调整。此建议不会自动修改本机已有配置。

本次发现并修复：`ProxyError::RateLimited` 在 Codex 的手工错误响应路径此前可能落到默认 500，且没有 `Retry-After`。现在最终返回 HTTP 429、`rate_limit_error` 和上游等待秒数，客户端可据此作下一步决定。

安装包验收还发现代理停止后旧 keep-alive 连接仍可处理请求，导致重新启动后的界面统计与实际处理实例不一致。代理现统一管理连接，停止时关闭并回收连接（包括等待请求头的空闲连接）；重启后的客户端需连接新实例。停止服务会终止尚未完成的请求，不自动重放已输出内容。

## 引入来源与验证

请求兼容逻辑参考并移植自 [yunhanhai/agentrouter-responses-shim-sentry-fix](https://gitee.com/yunhanhai/agentrouter-responses-shim-sentry-fix) 的固定提交 `ff6277e05beff1bfc61e2a3abc0741deb0d42b3c`，基础包为 `agentrouter-responses-shim@2.0.1`。它的 Node 服务、前缀路由、重试循环和出站代理不另行运行：YunSwitch 复用已有原生代理、路由与重试机制，新增的是 Rust 请求兼容处理、设置开关及边界验证。原 MIT 许可见 [AgentRouter-Responses-Shim-MIT.txt](../licenses/AgentRouter-Responses-Shim-MIT.txt)。

与给定补丁相比，本实现把递归范围限制在协议容器，并在清理之前保护压缩历史和状态引用，避免原补丁“先删密文、再检查状态”造成不可恢复信息丢失。

验证覆盖纯函数清理/保持不变、默认关闭与旧设置保存、官方和跨协议路径排除、模拟网关密文错误的开关对照、429 后再次发起请求成功、最终 429 HTTP 状态与头。所有请求使用回环地址和虚构密钥；未验证所有真实网站，也未使用私人配置或会话。

本机验证记录：Codex 相关 Rust 测试 625 项通过（1 项既有真实语料测试忽略）；代理相关回归 1512 项通过。这两组有重叠，不能相加。最后增加“仅剩空内容时拒绝”的边界后，清理模块 6 项再次通过，严格 Clippy 通过。前端 143 个文件、1092 项通过；App 模块加载超过默认 10 秒的 7 项集成测试单独以 60 秒初始化等待复验通过，仓库默认超时未修改。TypeScript、格式检查和前端构建通过。

新增 MIT 副本的便携包模拟打包、MSI 重新打包与行政提取检查通过；本机重新打包仅验证许可分发，不是包含新功能的正式发布安装包。
